## FR-001 — Диаризация: подписывать реплики «Говорящий 1..N»

**Статус:** `Proposed` (не реализовано, ждёт приоритета)  
**Дата:** 2026-10-20

### Запрос

Если в записи участвует несколько собеседников, распознавать это и подписывать
реплики:

```text
Говорящий 1: Привет, как дела?
Говорящий 2: Хорошо, спасибо. А у тебя?
```

Имена — «Говорящий 1», «Говорящий 2» и т.д. Если говорящий один, метки не нужны.
При постобработке метки должны сохраняться.

### Что проверили в whisper.cpp 1.9.5

- `--diarize` — **стерео-диаризация**. Нужен 2-канальный файл, где говорящие
  разведены по каналам. Внутри сравнивается энергия каналов, в текст добавляется
  `(speaker 0)` / `(speaker 1)`. Максимум 2 говорящих, только стерео.
- `--tinydiarize` — определяет **смену говорящего**, но не личность. Требует
  специальную модель `tdrz`, доступную только для английского. Имён не выдаёт.
- Полноценной диаризации «моно-запись, N говорящих, русский» в whisper.cpp нет.
- Приложение пишет моно 16 кГц, поэтому встроенный `--diarize` не даст меток.

### Предлагаемое решение

Интегрировать offline-диаризацию через **sherpa-onnx**:

- сегментация pyannote + speaker embeddings;
- работает с моно, русским языком и N говорящими;
- выдаёт временные отрезки с ID говорящих;
- сегменты Whisper (с таймкодами) сопоставляются с отрезками диаризации;
- метки «Говорящий 1..N» нумеруются по первому появлению;
- при одном говорящем метки не добавляются.

Изменения в приложении:

- настройка **«Разделять говорящих»** (по умолчанию выключена);
- выбор количества: **авто / 2 / 3 / 4**;
- скачивание моделей диаризации (~30–50 МБ) в общий менеджер моделей;
- при включении — запрос Whisper с таймкодами (`verbose_json`), отдельный шаг
  диаризации и склейка;
- HUD-состояние «Определяю говорящих…»;
- промпт: сохранять метки, не менять номера, не объединять реплики и не
  придумывать новых говорящих;
- `docs/testing.md`: новые сценарии (моно/стерео, 1/2/3 говорящих, русский,
  пересекающаяся речь, Intel/Apple Silicon).

### Альтернативы

1. **Стерео, 2 говорящих** — встроенный `--diarize`; быстро и без новых моделей,
   но нужен стерео-вход и максимум 2 собеседника.
2. **Tinydiarize** — только смена реплик, английский, без имён.
3. **Только промпт** — сохранять готовые метки, если они уже есть в тексте, но
   не определять говорящих.

### Критерии готовности

- [ ] Настройка включения/выключения диаризации.
- [ ] Поддержка моно-записи с обычного микрофона.
- [ ] Русский язык.
- [ ] 2–4 говорящих (минимум), номера по первому появлению.
- [ ] Один говорящий — без меток.
- [ ] Промпт сохраняет метки и не смешивает реплики.
- [ ] Работает на macOS 15+ (arm64 и Intel).
- [ ] Обработка не ломает обычную диктовку при выключенной настройке.
- [ ] Сценарии добавлены в `docs/testing.md`.

### Риски

- Размер моделей и бинарника; для Intel — дополнительная сборка.
- Дополнительные 2–10 секунд обработки.
- Пересекающаяся речь и шум ухудшают качество кластеризации.
- Число говорящих может определяться неверно; нужен ручной выбор 2/3/4.
- Модели диаризации нужно скачивать и проверять по SHA-256.

### Решение

Пока ничего не реализуем. Запись оставлена на будущее; при взятии в работу
обновить статус на `Planned` и добавить тестовые сценарии.

## FR-002 — Завершать запись нажатием Enter

**Статус:** `In progress`, реализация 1.1.8, проверяется.
**Дата:** 2026-11-12

### Согласованное поведение

Во вкладке «Хоткеи» добавлен отключаемый флажок
«Останавливать распознавание по нажатию Enter». По умолчанию выключен,
применяется после сохранения без перезапуска. Старые settings.json без
`stopRecordingOnEnter` также получают false. Сброс вкладки выключает функцию.

Return (36) и Enter цифрового блока (76) без модификаторов завершают только
активную запись. Они запускают существующий `stop()` — финализацию WAV,
Whisper/завершение потока Nemotron, AI и вставку. Это не отмена записи.

Поглощается одно физическое нажатие: keyDown, его autorepeat и keyUp, даже если
запись уже остановлена. Новые нажатия после отпускания сразу работают обычно,
в том числе во время финального распознавания. Блокировки до вставки нет.
Shift/Control/Option/Command+Enter и режим назначения хоткеев сохранены.

### Реализация и защита от гонок

`DictationKeyPolicy` хранит только захваченные коды клавиш и принимает решение
пропустить событие, поглотить, завершить или отменить конкретную сессию. Потерянный keyUp
не блокирует следующий свежий keyDown. Политика сохраняется при обновлении tap,
чтобы завершить уже захваченное физическое нажатие после сохранения настроек.

`HotkeyMonitor` слушает keyDown/keyUp, но основные хоткеи вызывает только на keyDown.
Для Enter он получает актуальный recordingSessionID из DictationSession,
передаёт его в отложенный callback. `finishRecording(expectedSessionID:)`
проверяет фазу и UUID перед вызовом существующего stop(), не вызывает toggle().
Запоздавшее событие не может начать или завершить другую запись.

Автоматические проверки используют синтетические события без установки tap,
публикации клавиш в систему или отправки сообщений в реальный чат.
Матрица регрессии и результаты — docs/testing.md, раздел 30.
Для реального перехвата нужен работающий CGEventTap с существующим Accessibility.
