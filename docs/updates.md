# Обновления приложения и выпуск через GitHub Actions

Runvoice проверяет подписанную ленту своего варианта сборки при запуске,
раз в сутки и вручную. После сетевой ошибки повтор выполняется через час.
Фоновая проверка не открывает окна. Оранжевая точка справа сверху на иконке
в строке меню обозначает доступное обновление и сохраняется при смене статусов.
Пункт меню и кнопка в «Основных» открывают стандартный интерфейс Sparkle.
Автоматическая загрузка и установка отключены; установка выполняется по кнопке.
Пропуск версии учитывается Sparkle, простое закрытие окна не снимает напоминание.

Перед установкой Runvoice ждёт завершения диктовки (включая паузу), улучшения
текста, записи сэмпла, проверки микрофона, загрузки моделей и API-очереди.
Ожидание можно отменить. Перед завершением приложения занятость проверяется
повторно; на этапе установки новые операции не принимаются, API возвращает 503.
Настройки, история, модели и сэмплы находятся вне заменяемого приложения.
Первую сборку со Sparkle нужно установить вручную; затем доступно обновление
из приложения. Выпуски подписываются постоянным сертификатом `Runvoice Local Signing`
(см. «Подпись релизов»), поэтому доступ к Keychain сохраняется между обновлениями.
Нотаризация Apple не выполняется: при первом открытии Gatekeeper потребует подтверждения.

## Однократная настройка GitHub

1. В репозитории `A11oW/runvoice` разрешите GitHub Actions.
2. Создайте environment **release** в Settings → Environments.
3. Настройте для него required reviewers и ограничьте выпуск доверенными тегами `v*`.
   Защитите изменения workflow и кода выпуска через review. Защита окружения
   настраивается владельцем репозитория; файл workflow сам её не создаёт.
4. Добавьте в **секреты окружения release** секрет `SPARKLE_PRIVATE_KEY`.
   Он содержит экспортированный закрытый ключ проекта в формате Sparkle (Base64).
   Это секрет, не repository variable. Не отправляйте его в переписку и не коммитьте.
5. Встроенный `GITHUB_TOKEN` получает `contents: write` только в задаче подписи
   и создания черновика. Личный GitHub-токен не требуется.

Окружение release передаёт ключ только задаче подписи после разрешения reviewers.
Код разрешённой задачи получает доступ к секрету: защита workflow и доверенных тегов
остаётся обязательной частью процедуры. В сборке, тестах и загружаемых артефактах
ключа нет. При ошибке ключа задача останавливается, неподписанный выпуск не создаётся.

## Подпись релизов

Релизы подписываются сертификатом `Runvoice Local Signing` с закрытым ключом.
Ключ хранится локально на машине владельца и в секретах окружения `release`.
Ad-hoc подпись в выпуске не публикуется: задача выпуска останавливается.

1. Добавьте в секреты окружения **release** два значения:
   - `RUNVOICE_SIGN_P12` — файл `.p12` в base64;
   - `RUNVOICE_SIGN_P12_PASSWORD` — пароль этого `.p12`.
2. Экспортируйте **только** сертификат `Runvoice Local Signing` на локальной машине:
   - откройте «Связка ключей», раздел «Мои сертификаты», выберите «Runvoice Local Signing»
     вместе с закрытым ключом;
   - «Файл → Экспортировать объекты…», формат «Personal Information Exchange (.p12)»,
     задайте пароль;
   - сохраните файл в защищённую папку вне Git.

   Команда `security export -t identities` выгружает все identity связки и не подходит:
   в секреты попадут чужие закрытые ключи.

   Проверьте файл, что в нём ровно один сертификат с отпечатком из скрипта:

   ```sh
   read -rs RUNVOICE_SIGN_P12_PASSWORD && export RUNVOICE_SIGN_P12_PASSWORD
   /usr/bin/openssl pkcs12 -in /защищённая/папка/runvoice-sign.p12 -nokeys \
     -passin env:RUNVOICE_SIGN_P12_PASSWORD | grep -c 'BEGIN CERTIFICATE'
   /usr/bin/openssl pkcs12 -in /защищённая/папка/runvoice-sign.p12 -nokeys -clcerts \
     -passin env:RUNVOICE_SIGN_P12_PASSWORD \
     | /usr/bin/openssl x509 -noout -fingerprint -sha1 \
     | sed 's/.*=//; s/://g' | tr 'A-F' 'a-f'
   ```

   На macOS используется системный `/usr/bin/openssl` (LibreSSL); Homebrew OpenSSL 3+
   требует для такого `.p12` флаг `-legacy`.

   Первая команда должна вывести `1`; вторая — `4ffe265ebd1f1e1d196faefb795df66c8c17585c`
   (нижний регистр без двоеточий), совпадающий с отпечатком в
   `scripts/sign-release.sh`. Затем создайте base64 и вставьте его в секрет
   `RUNVOICE_SIGN_P12`:

   ```sh
   base64 -i /защищённая/папка/runvoice-sign.p12 | pbcopy
   ```

   Буфер обмена очистите после вставки. Файл `.p12` не коммитьте и не передавайте
   в переписке; храните его только в защищённой резервной копии.
3. Задача выпуска импортирует сертификат во временную связку ключей, подписывает
   оба приложения и DMG (`scripts/sign-release.sh`) и проверяет, что
   certificate leaf совпадает с отпечатком `4ffe265e…` из скрипта. Временная
   связка удаляется в конце задачи.
4. Если секрет отсутствует или проверка не проходит, выпуск останавливается до
   создания черновика. Ничего не публикуется.

Ротация сертификата меняет certificate leaf. Тогда в скрипте нужно заменить
отпечаток, и каждому пользователю один раз потребуется подтвердить доступ к
Keychain. Такую замену указывайте в описании выпуска.

Локальная проверка подписи без публикации:

```sh
make app
scripts/sign-release.sh
```

## Резервная копия и перенос ключа

Ключ проекта хранится в Keychain под account `ai.opencode.runvoice.updates`.
Открытая часть закреплена в `SUPublicEDKey` приложения. Один закрытый ключ можно
использовать на нескольких доверенных компьютерах либо в GitHub Actions.
Право подписывать обновления эквивалентно праву выпускать исполняемый код пользователям.

Для экспорта выполните команды на своей машине, выбрав защищённую папку вне Git:

```sh
bash scripts/prepare-sparkle.sh
umask 077
.build/sparkle/bin/generate_keys --account ai.opencode.runvoice.updates -x /защищённая/папка/runvoice-update-key.txt
```

macOS может запросить пароль связки ключей. Вводите его только в системное окно.
Содержимое экспортированного файла вставьте в защищённое поле `SPARKLE_PRIVATE_KEY`
в GitHub. Храните отдельную резервную копию в защищённом хранилище; не оставляйте
временный экспорт в общедоступной папке. Приватный ключ нельзя восстановить по открытому.
При утрате ключа пользователям с текущей схемой доверия потребуется ручная установка.

Другой доверенный разработчик может импортировать экспорт в свою связку:

```sh
.build/sparkle/bin/generate_keys --account ai.opencode.runvoice.updates -f /защищённая/папка/runvoice-update-key.txt
```

`scripts/init-update-key.sh` предназначен для начальной настройки нового проекта
либо чтения существующего ключа. Не заменяйте ключ в уже распространяемом приложении
просто потому, что его нет в связке нового компьютера: импортируйте исходный.

## Подготовка и запуск выпуска

1. Увеличьте оба номера версии в `app/Info.plist` и перенесите изменения из
   «Не выпущено» в соответствующий раздел CHANGELOG. Номера должны совпадать.
2. Закоммитьте и отправьте код, создайте и отправьте тег `v<версия>`.
   Тег должен совпадать с метаданными. Публикация существующего публичного релиза
   повторно не выполняется и его вложения workflow не перезаписывает.
3. Workflow **Release Runvoice** запускается на теги `v*`. Его также можно запустить
   вручную из Actions с существующим тегом. Дождитесь сборки и тестов.
4. Reviewer окружения release разрешает задачу выпуска. Она импортирует сертификат
   подписи приложений (раздел «Подпись релизов»), подписывает оба приложения и DMG,
   проверяет закрытый и открытый ключи Sparkle, подписывает ZIP и appcast и создаёт черновик релиза.
5. Проверьте описание и вложения черновика, затем опубликуйте стабильный релиз
   и назначьте его **Latest**. Не отмечайте его как prerelease.

Сборка выполняется на macOS arm64; создаются оба варианта приложения, Intel
проверяется под Rosetta. Sparkle, whisper.cpp и VAD проверяются по закреплённым
версиям/контрольным суммам. Framework-ссылки и права файлов сохраняются в TAR
между задачами и в ZIP через `ditto`. UI-проверки с фактическими разрешениями
Accessibility и микрофоном остаются локальными сценариями тест-плана.

В релиз включаются два DMG и их SHA-256, два ZIP обновления и их SHA-256,
`appcast-arm64.xml` и `appcast-intel.xml`. Ленты содержат только этот выпуск,
точные ссылки на ZIP по тегу и описание из CHANGELOG; черновик не виден клиентам.
Приложения читают постоянный адрес
`https://github.com/A11oW/runvoice/releases/latest/download/appcast-<вариант>.xml`.
Архив и лента подписаны EdDSA. Подпись проверяется до распаковки.

## Локальная подготовка и проверки

При необходимости те же файлы можно подготовить локально после сборки:

```sh
python3 scripts/release-notes.py > .build/release-notes.txt
python3 scripts/prepare-updates.py --notes .build/release-notes.txt
```

По умолчанию используется Keychain. `--key-file` позволяет явно выбрать защищённый
файл экспорта; в CI скрипт читает `SPARKLE_PRIVATE_KEY`, создаёт временный файл
с правами 0600 и удаляет его после завершения процесса. Закрытый ключ не выводится
и не передаётся аргументом командной строки. Скрипт ничего не публикует самостоятельно.

```sh
make test-updates
python3 scripts/test-update-install.py
```

Первый набор использует подставной backend без сети. Второй создаёт одноразовый
тестовый ключ и две изолированные тестовые копии, обслуживает подписанный appcast
через localhost и проверяет замену, перезапуск, ожидание занятости, сохранность
тестовых данных и отказ для повреждённого архива. Рабочий ключ и установленный
Runvoice не используются. Артефакты проверки находятся в `.build/updater/`.

Опубликованные выпуски и ещё не выпущенные изменения перечислены в [CHANGELOG](../CHANGELOG.md).
